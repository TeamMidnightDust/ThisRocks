# This Rocks! — Minecraft 26.2 Fabric port

Date: 2026-08-07
Status: approved, ready for implementation planning

> This document is fork-local. Exclude `docs/superpowers/` from any pull request
> offered to `TeamMidnightDust/ThisRocks`.

## Goal

Port `TeamMidnightDust/ThisRocks` from Minecraft 1.21.11 to Minecraft 26.2 on
Fabric, keeping the mod's Polymer server-side mode intact, and produce a jar
that runs in the user's PrismLauncher 26.2 instance.

## Provenance

Base: upstream branch `1.21.11`, commit `6a566e1` ("port: Mounts of Mayhem
(1.21.11)", 2025-12-12). Upstream has no 26.x work. License is MIT, so the fork
is unencumbered; `LICENSE` and authorship metadata stay verbatim.

Fork: `Arilas/ThisRocks`, branch `port/26.2-fabric`, working tree at
`/Volumes/Dev/Projects/krona/minecraft-mods/ThisRocks`.

Mod version moves from `1.9.4+1.21.11` to `1.9.4+26.2`.

## Baseline measurements

- 54 Java files, 3,246 lines, single Fabric source set.
- 352 resource files: 286 datagen output under `src/main/generated`, 66 hand-authored
  under `src/main/resources`.
- No mixins in the source tree. `src/main/resources/rocks.mixins.json` names a
  client mixin class that does not exist and is not referenced from
  `fabric.mod.json`, so it is never loaded.
- `thisrocks.accesswidener` contains one entry, for the Yarn-named client class
  `net/minecraft/client/render/model/json/ModelElement$Deserializer`. It existed
  only for that dead mixin.

## The central constraint

Yarn mappings stop at `1.21.11+build.6`. There is no Yarn for 26.x. Polymer's
26.2 artifacts are compiled against Mojang names — verified by reading the
constant pool of `polymer-core-0.17.3+26.2.jar`, which references
`net/minecraft/world/level/block/Block` and `net/minecraft/core/BlockPos`.

The port is therefore two simultaneous migrations: Yarn to Mojang mappings, and
1.21.11 to 26.2. Every import in all 54 files changes.

All verified present on their respective mavens, and all 20 dependency classes
the mod imports were checked against the downloaded 26.2 jars.

- `eu.pb4.polymer.core.api.item.PolymerItemGroupUtils` →
  `eu.pb4.polymer.core.api.item.PolymerCreativeModeTabUtils`
- `PolymerSyncUtils.removeCreativeTab` → `removeItemGroup`

Both follow Polymer applying the vanilla `ItemGroup` → `CreativeModeTab` rename
to its own API surface.

## Approach

Two phases, each independently verifiable. Phase 1 is mechanical and
diff-reviewable; phase 2 is policed by the compiler.

### Phase 1 — mechanical class remap

A throwaway script under `tools/` in this repository (not shipped in the jar)
builds a Yarn → Mojang **class-name** dictionary for 1.21.11 by joining three
published artifacts on the obfuscated name:

- `net.fabricmc:intermediary:1.21.11:v2` — tiny v2, `official → intermediary`
- `net.fabricmc:yarn:1.21.11+build.2:v2` — tiny v2, `intermediary → yarn`
- Mojang's 1.21.11 `client.txt` ProGuard mappings — `mojang → official`,
  reachable from the version manifest

The yarn build **must** be `build.2`, the build pinned in `gradle.properties`.
Later builds rename `net.minecraft.util.collection.Pool` to `WeightedPool`,
which leaves `datagen/Models.java`'s import unresolvable. Verified: against
`build.2`, all 103 distinct vanilla imports in the codebase resolve; against
`build.6`, one does not.

The dictionary is applied to imports and type references only. Class-level is
the deliberate safety boundary: a wrong class name fails to compile, whereas a
wrong method name can bind to a same-shape overload and fail silently at
runtime. The result is one commit that does not yet compile but can be reviewed
as a pure rename diff.

### Phase 2 — compiler-driven 26.2 migration

Point the build at 26.2 and work the error list. Every unresolved name is
resolved against the decompiled 26.2 sources in the local neoformruntime cache,
not guessed.

`Identifier` needs no phase-2 work: 1.21.11 Mojang mappings already place it at
`net.minecraft.resources.Identifier`, so phase 1 handles it.

Known 26.2 changes that land in this codebase:

- `PayloadTypeRegistry.playC2S()` → `serverboundPlay()` (`RocksMain`).
- `BlockEntityType` constants → `BlockEntityTypes`.
- `ResourceKey.getValue()` / `.location()` → `.identifier()`, used throughout
  `FeatureInjector`'s biome predicates.

The `ValueInput`/`ValueOutput` entity-save migration does **not** apply: both
geyser block entities hold `countdown` as transient field state with no NBT read
or write.

### Rejected alternatives

**Pure compiler-driven, no dictionary.** Roughly 1,000 first-pass errors with
every import wrong. Each guess that happens to compile becomes a silent runtime
bug — the same failure class as the DT add-on branch loot tables.

**Full method- and field-level remap pipeline.** Member renames need
signature-aware rewriting to be safe, and the pipeline still cannot touch the
1.21.11 → 26.2 drift, so phase 2 would happen anyway. Not justified at
3,246 lines.

## Build configuration

- Fabric Loom `1.17.17`, Gradle wrapper `9.5.1`, Java 25 toolchain.
- `mappings loom.officialMojangMappings()` replaces the Yarn `mappings` line.
- Every `modImplementation` becomes plain `implementation`. Loom 1.17 on 26.x
  has no `modImplementation`/`modCompileOnly` and performs no remapping.
- Deleted: `rocks.mixins.json`, `thisrocks.accesswidener`, the `accessWidener`
  key in `fabric.mod.json`, and the `loom.accessWidenerPath` line.
- `fabric.mod.json` `depends` becomes `fabricloader >=0.19.3`, `minecraft 26.2`,
  `fabric-api *`.

Two build items to be resolved by verification rather than assumption, each
recorded in `PORTING-NOTES.md` whichever way it lands:

1. MidnightLib is currently jar-in-jarred via `include(...)`. If `include`
   misbehaves under Loom 1.17's no-remap configuration, MidnightLib becomes a
   hard `depends` entry and ships alongside the mod.
2. `me.shedaniel.unified-publishing 0.1.+` predates Gradle 9. If it fails to
   configure, the publishing block is removed — it is release tooling, not port
   work.

## Polymer

Ported, not stripped. Beyond the `PolymerCreativeModeTabUtils` rename and
`PolymerSyncUtils.removeItemGroup`, remaining drift is method signatures inside
otherwise-unchanged classes, which the compiler surfaces.

`PolyUtil.hideElementHolders` reaches into `eu.pb4.polymer.virtualentity.impl.HolderHolder`,
an implementation class rather than API. It survived to 0.17.3, but the
dependency on a non-API type is recorded in `PORTING-NOTES.md` as a known
fragility for future updates.

## Datagen and resources

Datagen is retained and is the reason this port is lower-risk than the DT
add-ons: `assets/rocks/items/*.json` item model definitions — the file class
whose absence silently broke DynamicTrees-BOP and DynamicTrees-Terralith on
26.2 — are generated here, not hand-maintained.

All 286 files under `src/main/generated` are deleted and regenerated by
`runDatagen` against 26.2. The regenerated tree is diffed against the 1.21.11
baseline to catch silently dropped entries.

`datagen/Models.java` is the highest-risk single file. It drives the newest
vanilla model API (`ModelVariant`, `WeightedVariant`, `AxisRotation`, `Pool`,
`TextureKey`), all of which moved in the 26.2 renderer rework.

## Verification

1. `./gradlew build` produces a jar in `build/libs`.
2. `./gradlew runDatagen` completes; regenerated resources are diffed against
   the 1.21.11 baseline and the diff is reviewed for dropped entries.
3. A repository-local `tools/audit_jar.py` check. The existing
   `../tools/audit_mod_jar.py` at the minecraft-mods root is **not** reusable —
   it exposes only `compat`, `immersive-weathering`, and `data-only` profiles,
   all with hardcoded mod ids and dependency sets that do not apply here.
4. Install into the PrismLauncher 26.2 instance and launch, confirming in a
   fresh world: rocks and sticks generate, the creative tab is populated, the
   MidnightLib config screen opens, and a geyser applies levitation.

Polymer mode is server-side and cannot be exercised from a client launch. It
will be confirmed to initialize without error and reported as **untested**, not
as working.

## Risks, ranked

1. `datagen/Models.java` against the reworked 26.2 model API.
2. Polymer method-signature drift beyond the one class rename.
3. `ParticleUtil`'s `ParticleS2CPacket` constructor, which changes shape most
   versions and depends on an unchecked `ParticleType` → `ParticleEffect` cast.
4. Fabric's `BiomeModifications` API surface in fabric-api 0.155.2
   (`FeatureInjector`).
5. MidnightLib `include` under Loom 1.17.

## Out of scope

- NeoForge support. The mod is Fabric-native and stays Fabric-only.
- Restoring the dead mixin and its access widener entry.
- Any gameplay or content change. This is a port; behaviour matches 1.21.11.
- Opening the upstream pull request. The fork is kept PR-able, but the decision
  to offer it is the user's and comes after playtesting.
